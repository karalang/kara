# Fixtures that FAIL the memory_sanitizer suite at KARAC_OPT_LEVEL=0 and PASS
# at the default -O2. Consumed by scripts/asan-o0-leg.sh. B-2026-08-04-17.
#
# Every entry names the bug row that owns it. Nothing goes on this list without
# one — an unattributed entry is indistinguishable from a fixture someone
# silenced.
#
# THE LIST ONLY SHRINKS. scripts/asan-o0-leg.sh fails both when an unlisted
# fixture starts failing (a regression) and when a listed one starts PASSING
# (the owning bug got fixed and the line is now stale). That second direction is
# what keeps this from decaying into a permanent allowlist.
#
# These are NOT -O0-only curiosities dismissible as debug-build noise. At -O0 no
# pass pipeline runs, so the allocations the fixture intends actually happen;
# at -O2 the same buffers are provably dead and LLVM deletes them, which is why
# the fixture passes there. The leak is in the emitted code either way — -O2
# just deletes the evidence along with the allocation.
#
# Measured 2026-08-06 at 225a4553, x86_64 Linux, both archives rebuilt
# lean-then-full: 942 passed / 4 failed / 10 ignored in 92s.

# B-2026-08-05-7's tensor entry (asan_tensor_lifecycle_clean) was REMOVED
# 2026-08-06: the fresh-temp owned-argument leak it named is fixed. Owned tensor
# params are caller-retains like Vec/String, and the caller-side materialization
# that covers those is gated on the Vec `{ptr,len,cap}` LLVM shape, which a
# tensor — a bare `ptr` to one `[rank][dims][data]` block — is not. It now gets
# its own caller-scope `FreeTensor` behind the same passthrough guard.
#
# Not an -O0 curiosity either: with a callee that reads the WHOLE block
# (`t.sum()` rather than `t[0, 0]`) the leak measures 2,240 B / 40 blocks
# IDENTICALLY at -O0 and at the default -O2. The fixture read it one element at
# a time, which is what let LLVM delete the allocation and made it look
# -O0-only. `asan_tensor_fresh_temp_owned_arg_no_leak` carries the summing form
# so the default leg gates it too.

# B-2026-08-05-7's nested-Option entry
# (asan_nested_option_pattern_boxed_payload_lifecycle_clean) was REMOVED
# 2026-08-06: all three of its boxes now have owners. Its old line here read
# "`Wrap.W(Option.Some(s))` orphans the box; the control that never matches it
# out is clean" — that attribution was wrong and is worth recording, because it
# pointed at the wrong site. The box leaks on CONSTRUCTION: the same value
# matched with a bare `_` leaks identically (measured 288 B / 9 at HEAD before
# the fix). The fixture's "clean control" is a different VALUE — a named
# `Option[Option[String]]` whose let-site box drop does own its box — not the
# same value left unmatched.
