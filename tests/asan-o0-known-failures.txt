# Fixtures that FAIL the memory_sanitizer suite at KARAC_OPT_LEVEL=0 and PASS
# at the default -O2. Consumed by scripts/asan-o0-leg.sh. B-2026-08-04-17.
#
# Every entry names the bug row that owns it. Nothing goes on this list without
# one — an unattributed entry is indistinguishable from a fixture someone
# silenced.
#
# THE LIST ONLY SHRINKS. scripts/asan-o0-leg.sh fails both when an unlisted
# fixture starts failing (a regression) and when a listed one starts PASSING
# (the owning bug got fixed and the line is now stale). That second direction is
# what keeps this from decaying into a permanent allowlist.
#
# These are NOT -O0-only curiosities dismissible as debug-build noise. At -O0 no
# pass pipeline runs, so the allocations the fixture intends actually happen;
# at -O2 the same buffers are provably dead and LLVM deletes them, which is why
# the fixture passes there. The leak is in the emitted code either way — -O2
# just deletes the evidence along with the allocation.
#
# Measured 2026-08-06 at 225a4553, x86_64 Linux, both archives rebuilt
# lean-then-full: 942 passed / 4 failed / 10 ignored in 92s.
#
# THE LIST IS NOW EMPTY (2026-08-06). All four entries are fixed, each removal
# recorded below with the mechanism rather than deleted silently. The leg still
# gates: with nothing quarantined, ANY -O0 failure is a new failure.

# B-2026-08-05-7's tensor entry (asan_tensor_lifecycle_clean) was REMOVED
# 2026-08-06: the fresh-temp owned-argument leak it named is fixed. Owned tensor
# params are caller-retains like Vec/String, and the caller-side materialization
# that covers those is gated on the Vec `{ptr,len,cap}` LLVM shape, which a
# tensor — a bare `ptr` to one `[rank][dims][data]` block — is not. It now gets
# its own caller-scope `FreeTensor` behind the same passthrough guard.
#
# Not an -O0 curiosity either: with a callee that reads the WHOLE block
# (`t.sum()` rather than `t[0, 0]`) the leak measures 2,240 B / 40 blocks
# IDENTICALLY at -O0 and at the default -O2. The fixture read it one element at
# a time, which is what let LLVM delete the allocation and made it look
# -O0-only. `asan_tensor_fresh_temp_owned_arg_no_leak` carries the summing form
# so the default leg gates it too.

# B-2026-08-05-7's nested-Option entry
# (asan_nested_option_pattern_boxed_payload_lifecycle_clean) was REMOVED

# B-2026-08-07-12's entry
# (asan_struct_field_boxed_payload_interior_match_out_no_double_free) was
# REMOVED 2026-08-07, and THE LIST IS EMPTY AGAIN. The ratchet found it in the

# This one line outlived THREE distinct causes, worth recording because each
# time it looked like the last:
#   1. B-2026-08-07-7's arm zeroed the struct field's tag to stop a double free,
#      and that same tag guards the envelope free — 32 B per consuming
#      construction. Fixed by parking the box and releasing it box-only on the

#   2. What remained was the fixture's four BY-VALUE calls per iteration, whose
#      callee entry copy duplicated the box and SHARED the `String` inside it.
#      Fixed as B-2026-08-07-12's two roots.
#   3. What remained after THAT was one call per iteration —
#      `scalar(V { o: Some(Some(n + i)) })`, an ALL-SCALAR boxed payload. The
#      caller-scope gate declined it correctly on heap grounds; that envelope is
#      heap by no predicate's reckoning but the allocator's. Closed once
#      B-2026-08-07-2 shape 3 gave the field a drop, which is what let
#      `option_field_te_has_drop_heap` answer yes.
#
# The lesson rounds 2 and 3 paid for: "my fix should empty this line" is a
# prediction to MEASURE. Twice the arithmetic said otherwise, and both times the

# ── 2026-08-12: the list went NON-EMPTY and is EMPTY again the same day. ──
#
# B-2026-08-12-15's entry
# (asan_struct_field_boxed_heapless_option_envelope_owned) was REMOVED
# 2026-08-12, one commit after it was added: the boxed `Option` FIELD envelope
# inside an inline STRUCT payload now has an owner in every frame that does not
# consume it. THE LIST IS EMPTY, so any -O0 failure from here on is a new one.
#
# Worth recording because the entry was filed with the WRONG CAUSE, which four
# failed fixes were aimed at. It blamed c24343b3 (B-2026-08-12-1's by-value
# param entry copy) and the by-value CALL. Both were wrong, and one probe said
# so: `let r: Result[W, i64] = Result.Ok(W { o: Option.Some(Option.Some(n)) });`
# leaks 32 B per construction with NO CALL ANYWHERE IN THE PROGRAM. The entry
# copy only removed an ACCIDENTAL owner (the callee's arm, which used to free
# the caller's envelope) from one of the forms; the gap was in the type walk and
# predated it.
#
# The three sites that now own it, each measured against a shape the others miss:
#   * the let site, for every form that binds the value;
#   * the fresh-temp argument spill, for the one form that does not;
#   * the consuming arm, which takes it over from the scrutinee — the arm's
#     `__karac_drop_struct_<T>` already frees the box, so without a handoff the
#     let-site fix turns the leak into a double free.
#
# The enumeration is `struct_payload_boxed_field_variants`, third sibling of
# `boxed_enum_payload_variants` and `nested_boxed_enum_payload_variants`. It
# needed no new cleanup action: `NestedBoxedEnumDrop` was already parameterized
# on the inner tag's field index, and a struct payload only shifts that index by
# the words of the fields ahead of the box.

# B-2026-08-12-19 — the CALLEE's entry copy of a `Result[S, i64]` whose struct
# payload has a boxed `Option` field, when the callee's arm binds NOTHING.
# `fn cls(r: Result[S, i64]) { match r { Result.Ok(_) => 1, … } }` over
# `struct S { o: Option[Option[String]] }`: the copy's box and the String
# inside it are both malloc'd in `cls` and freed by nobody — 1,391 B in 80
# allocations over 40 iterations, attributed to `cls` in the LSan trace.
#
# CALLER-SIDE IS CLEAN, which is why this passes at -O2 and only shows here:
# the copy is dead and LLVM deletes it. B-2026-08-12-18 fixed the caller's
# interior in every position including this one, and the measurement brackets
# it — pre-fix -O0 reports 1,551 B / 120 allocations, post-fix 1,391 B / 80.
# The 160 B / 40 difference is exactly the caller-side Strings that row closed;
# the remainder predates it and is untouched.
#
# WHY IT IS ITS OWN FIXTURE rather than a leg of the -18 matrix: quarantine is
# per-test, so folding this shape in would blanket the six positions that ARE
# fixed and are green at both levels.
#
# THE FIX IS NOT "register the struct-field population callee-side". That is
# what `functions.rs` deliberately declines, and its comment records the
# measurement: for a copy-supported payload the callee's arm already runs
# `__karac_drop_struct_<T>`, so registering makes two owners and aborts with a
# glibc double free on the temp-argument, bound-argument and matched-after-call
# forms. The gap is narrower — an arm that binds nothing leaves the copy with
# no owner — so any fix has to be conditional on that, not on the population.
